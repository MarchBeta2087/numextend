# contrib/nex_ooc：out-of-core 分块乘法原型（P1b-OOC，issue #104）

默认不构建；由 `-DNEX_ENABLE_BIGNUM=ON` 一并构建（与 `nex_bigint_block` 同组），
不进核心 `libnex`、`nex_modules.txt`、子集闭包与 amalgam。

```bash
cmake -S . -B build-bignum -DNEX_ENABLE_BIGNUM=ON -DCMAKE_BUILD_TYPE=Release
cmake --build build-bignum -j
ctest --test-dir build-bignum -R nex_ooc_test --output-on-failure

# 10 亿位 × 小乘数，并用 schoolbook 参考逐位校验（峰值 RSS ≈ 164 MB）
./build-bignum/contrib/nex_ooc/nex_ooc_bench 1e9 23 --small 3

# 中小规模「大 × 大」，与内存内 AUTO（CRT NTT）逐位比对
./build-bignum/contrib/nex_ooc/nex_ooc_bench 1e7 17 --verify-direct
```

## 算法

操作数与结果都是**纯肢体文件**（小端 32-bit 肢序列，无头），块长 `L`：

```
a = Σ a_i·B^(iL)，b = Σ b_j·B^(jL)，B = 2^32
a·b = Σ_k B^(kL)·( Σ_{i+j=k} a_i·b_j )
```

按 `k` 升序生成输出块：块 `k` 的累加器只需 `2L+2` 肢，低 `L` 肢立即写盘，
高位（≤ `L+2` 肢）作为进位进入块 `k+1`。**峰值内存 O(L)，与操作数规模无关**。

- 块对乘法直接复用核心 AUTO 分派（块内为 Karatsuba / Toom-3 / CRT NTT）；
- 结果按「最后一个非零肢」裁剪（规范化），符号与零由 `nex_ooc_bin_mul`
  按常规规则处理；
- 只做顺序 I/O：每个 `a_i`/`b_j` 块被重复读取，读放大 = `min(na,nb)`。

```c
nex_ooc_err_ty nex_ooc_mul_files(const char *dst_path,
        const char *a_path, size_t a_limbs,
        const char *b_path, size_t b_limbs,
        const nex_ooc_opts_ty *opts, nex_ooc_stats_ty *stats);
nex_ooc_err_ty nex_ooc_bin_mul(bigint_bin_ty *dst,
        const bigint_bin_ty *lhs, const bigint_bin_ty *rhs,
        const nex_ooc_opts_ty *opts, nex_ooc_stats_ty *stats);
```

`opts.block_limbs`（默认 `2^23` 肢 = 32 MB）、`opts.scratch_dir`、
`opts.keep_temps`；`stats` 给出块数、块对数、磁盘读/写字节、结果肢数与耗时。

基准的三个校验开关：

- `--small k`：`b = k`，用分块 schoolbook 逐位比对（内存 O(chunk)，可跑到 1e9 位）；
- `--verify-direct`：内存内完整乘一遍再逐块比对（需容纳完整乘积：1e8 位约 1 GB；
  受直接 NTT 上限 `s ≤ 2^27` 限制，**1e9 位不可用**——1e9 位需要 `s = 2^29`）；
- `--verify-mod`：流式对 5 个素数（2^31−1、2^31−13、…、998244353）检查
  `(a mod p)·(b mod p) ≡ (a·b) mod p`，内存 O(chunk)，可跑到任意规模（M2 的校验手段）。

注意 `file_mod_u32` 按 `Σ limb_i·B^i mod p` 累加（文件是小端肢序，不能用
从最低肢开始的 Horner 递推——该错误在开发中已由 Python 大整数对拍发现）。

## 实测（Windows i5-13500H，Release/-O2，单线程）

| 规模 | 块长 | 块对 | 耗时 | 峰值 RSS | 校验 |
|---|---:|---:|---:|---:|---|
| 1e7 × 1e7 | 2^17（131k 肢） | 8×8=64 | 19.9 s | 16.3 MB | 内存 NTT 逐位一致（+5.6 s） |
| 1e8 × 1e8 | 2^23（8.4M 肢） | 2×2=4 | 227.0 s | 651.5 MB | 内存 NTT 一致（+170.2 s） |
| 1e9 × 1e9 | 2^25（33.6M 肢） | 4×4=16 | **6648.9 / 6992.8 s** | **2692 MB** | 5 素数流式通过 |
| 1e9 × 3 | 2^23（8.39M 肢） | 13×1=13 | 1.1 s | 164.0 MB | schoolbook 一致（+0.4 s） |
| 单块 2^26 | 67.06M 肢 | 1×1=1 | **1092.8 s** | **4611 MB** | （仅测块对成本，无校验） |

参考：内存内 1e8 位直接 NTT 195.8 s / 930 MB（`bench/bench_huge`），
1e9 位三分块 2403 s / 6.24 GB（`contrib/nex_bigint_block`）。
注：1e9 × 1e9 跑了两次（6648.9 s 与 6992.8 s，输入由固定种子确定、
完全相同），跑间波动约 5%；第二次带 `--verify-mod`，5 素数校验通过（25.7 s）。

## M1 结论与 M2 的量级

1. **框架可行**：块切分 → 块积 → 磁盘进位链 → 规范化裁剪全部走通；
   1e9 位数（103,810,253 肢）在 164 MB 峰值下完成并与 schoolbook 逐位一致
   （注意：该例 `b = 3`，只验证进位链，**不覆盖 1e9 规模的块对 NTT**）。
2. **总时间 ≈ `pairs × P(L)`，`pairs = na·nb`，`P(L)` 是单个 L×L 块积的
   耗时**。固定 n 时 `pairs ∝ nb²`、`P(L) ∝ L ≈ n/nb`，故总时间随 nb
   **近似线性增长**（实测，n = 1e7 位 = 1,038,103 肢）：

   | nb | L（肢） | pairs | 耗时 | P(L) |
   |---:|---:|---:|---:|---:|
   | 1 | 1,048,576 | 1 | 4.6 s | 4.60 s |
   | 2 | 524,288 | 4 | 6.6 s | 1.65 s |
   | 4 | 262,144 | 16 | 11.7 s | 0.73 s |
   | 8 | 131,072 | 64 | 19.6 s | 0.31 s |
   | 16 | 65,536 | 256 | 26.3 s | 0.10 s |
   | 32 | 32,768 | 1,024 | 50.0 s | 0.05 s |

   每次 nb 翻倍耗时 ×1.34–1.9（平均 ~1.6），即 `nb·n·log(n/nb)` 的量级
   **得到实测支持**；且该模型偏保守（用 `L log L` 从 nb=1 外推 nb=8 得
   31 s，实测 19.6 s）。
3. **`P(L)` 在大 L 段超线性**。三个大 L 锚点（全部实测）：

   | L（肢） | 来源 | P(L) |
   |---:|---|---:|
   | 8.39M（2^23） | 1e8 大×大，2×2 块（227.0 s / 4） | 56.8 s |
   | 33.55M（2^25） | 1e9 大×大，4×4 块（6648.9–6992.8 s / 16） | 415.6–437.1 s |
   | 67.06M（2^26） | 单块对直测 | 1092.8 s |

   8.39M → 33.55M：L 翻 4 倍、P 涨 7.3 倍（`L log L` 预测 4.3×）；
   33.55M → 67.06M：L 翻 2 倍、P 涨 2.5 倍（预测 2.1×）。即 `P` 在
   中等 L 处 ∝ `L^1.47`，到 2^26 附近回落到 ∝ `L^1.32`。**不能用中小 L 的
   `L log L` 外推大 L，必须用大 L 实测锚点。**
4. **块数（此前写错，已更正）**：1e10 位 = 1.0381e9 肢，
   - `L = 2^23`（8.39M 肢）→ nb = **124**、pairs = 15,376；
   - `L = 2^25`（33.55M 肢）→ nb = 31、pairs = 961；
   - `L = 2^26`（67.1M 肢，直接 NTT 上限 `s ≤ 2^27` 允许的最大块）
     → nb = 16、pairs = 256。
5. 由此，**"朴素分块在 34 GB 下不可行"的说法不成立**。**目标块长
   `L = 2^26` 已直测**（1092.8 s、峰值 4611 MB），1e10 位只差「块对数
   线性」这一步（已在小规模 nb=1…32 验证）：

   | L | nb | pairs | 时间 | 峰值 RSS |
   |---:|---:|---:|---:|---|
   | 2^23 | 124 | 15,376 | 242 h（10 天） | ~0.7 GB（同块长实测） |
   | 2^25 | 31 | 961 | 111 h（4.6 天） | 2.7 GB（同块长实测） |
   | 2^26 | 16 | 256 | **77.7 h（3.2 天）** | **~4.6 GB（同块长实测）** |

   `L = 2^26` 是直接 NTT 上限（`s ≤ 2^27`）允许的最大块；**34 GB 够**
   （4.6 GB 实测 + 结果落盘不占内存），磁盘需求 4.15 + 4.15 + 8.3 GB。
   M2 的验收**不设时间上限**，所以 M2 可行，只是「3 天级」不是「小时级」。
   要压到小时级才需要块级 Karatsuba/FFT（见下）。
6. 待补（M2b/M3）：块缓存（读放大从 `nb` 降到 1）、并行块对、
   `mmap` 替代 `fread`；以及 1e10 端到端一次真实运行。

## M2 路线（按实测修订）

- **M2a（保底，先做）**：沿用现有朴素分块，`L = 2^26`、 16 块、256 块对
  → 256 × 1092.8 s = **77.7 h（3.2 天）**、峰值 **~4.6 GB（实测）**；
  结果用 `--verify-mod`（已实现，5 素数流式）+ 肢数检查验收。所需只是
  磁盘 4.15 + 4.15 + 8.3 GB 与一次 3 天无人值守运行（三处数据都已实测，
  只剩「块对数线性」假设）。
- **M2b（提速，可选）**：块级 Karatsuba——16 个块按 3 子积递归合并
  （4 层）→ 81 个叶子积而非 256，理论 ~3× 提速到 ~1 天；代价是每层要把
  「块和」物化到磁盘（每层 O(n) I/O），峰值内存 O(L)。
- **不建议**在 M2 做块级 FFT：那实质就是 #102 的 SSA（把块当系数再做一次
  变换），应与其 M3 合并决策，避免两条线各自造一遍。
